#! Analyzing the Angular Project Structure
1. The root directory of the project contains configuration files such as `angular.json`, `tsconfig.json` and `package.json`.
2. src directory contains all the source code files. index.html is the main entry point of the application. styles.css is the main CSS file. main.ts is the main TypeScript file which is very important as it is the first code file to be executed when your angular application starts.
3. assets directory contains all the static assets such as images, fonts, etc.

#! Understanding Components and how contents ends up on the screen
1. index.html gets its custom components tags from main.ts file. The main.ts imports the required components from the app directory. The app directory contains all the components inside app.components.ts file.
** app.components.ts file:**
```
import { Component } from '@angular/core';
import { RouterOutlet } from '@angular/router';

#! @Component is a decorator used to add metadata about the component.
@Component({
  selector: 'app-root',
  standalone: true,
  imports: [RouterOutlet],
  templateUrl: './app.component.html',
  styleUrl: './app.component.css'
})
export class AppComponent {
  title = 'first-angular-app';
}
```

#! Introducing Signals
** user.component.ts:**
"
import { Component, computed, signal } from '@angular/core';
import { DUMMY_USERS } from '../dummy-users';

const randomIndex = Math.floor(Math.random() * DUMMY_USERS.length);

@Component({
  selector: 'app-user',
  standalone: true,
  imports: [],
  templateUrl: './user.component.html',
  styleUrl: './user.component.css'
})

export class UserComponent {
  // selectedUser = DUMMY_USERS[randomIndex]; // Advantage of doing this is that we can now access this selectedUser inside the template of this component.
  selectedUser = signal(DUMMY_USERS[randomIndex]); //! using signals for state management
  imagePath = computed(() => `assets/users/${this.selectedUser().avatar}`); //! using computed for state management which uses signals under the hood

  //! This is a getter
  // get imagePath() {

    const randomIndex = Math.floor(Math.random() * DUMMY_USERS.length);

    this.selectedUser.set(DUMMY_USERS[randomIndex]); //! using signal's set method
  }
}

#! Working with Outputs and Emitting Data
When the user's click event is triggered, the onSelectUser method from user.component.ts is called. The emitted signal is then sent to the (select) event emitter. The (select) event then sends the emitted signal to the onSelectUser method of app.component.html which sends the emitted signal to the onSelectUser method from the app.component.ts which then console.logs the selected user's id.

** user.component.ts:**
```
import { Component, computed, EventEmitter, Input, input, Output, signal } from '@angular/core';

@Component({
  selector: 'app-user',
  standalone: true,
  imports: [],
  templateUrl: './user.component.html',
  styleUrl: './user.component.css',
})
export class UserComponent {
  //! Input decorator is used to receive data from the parent component to this child component
  @Input({required: true}) id!: string;
  @Input({required: true}) avatar!: string;
  @Input({required: true}) name!: string;

  //! Output decorator is used to send data from the child component to the parent component. In this case, it emits the id of the selected user. select is a custom named event
  @Output() select = new EventEmitter();

  //! This is a getter function
  get imagePath() {
    return `assets/users/${this.avatar}`;
  }

  onSelectUser() {
    this.select.emit(this.id);
  }
}
```
** user.component.html:**
```
<div>
    <button (click)="onSelectUser()">
        <!-- When using signals, we need to use parenthesis. For getter, we don't need parenthesis -->
        <img [src]="imagePath" [alt]="avatar">
        <span>{{ name }}</span>
    </button>
</div>
```

    if (tasks) {
      this.tasks = JSON.parse(tasks);
    }
  }

  getUserTasks(userId: string) {
    return this.tasks.filter((task) => task.userId === userId);

  }

  removeTask(id: string) {
    this.tasks = this.tasks.filter((task) => task.id !== id);

    this.saveTasks();
  }

  private saveTasks() {
    localStorage.setItem('tasks', JSON.stringify(this.tasks));

#! Module Summary
Here’s a short summary of the Angular module you provided, broken down into key points:

### Components
- **Components** are the building blocks for user interfaces in Angular.
- A **Component** is a class decorated with the `@Component` decorator, which contains the selector, template, styles, standalone and imports.
- **Component Tree**: Components can be nested within each other, forming a tree structure.
- **Inputs** allow a parent Component to pass data to a child Component.
- **Outputs** allow a child Component to send data or events back to the parent.

### Data Binding
- **String Interpolation**: Output property values in the template using `{{property}}`.
- **Property Binding**: Set a DOM property, like `src`, with `[property]="value"`.
- **Event Binding**: Listen to events (like clicks) using `(event)="method()"`.
- **Two-Way Binding**: Sync data between a form input and the model using `[(ngModel)]`.

### State Management
- **Zone.js** (default) watches for data changes and updates the UI.
- **Signals** (from Angular v16) require manual notifications of data changes, improving performance by targeting specific data updates. Also covered computed function.

### Conditional Rendering & Loops
- **@if Syntax** (from Angular v17) for conditional rendering, or use `ngIf` in earlier versions.
- **@for Syntax** (from Angular v17) for looping over arrays in templates, or use `ngFor` in earlier versions.

### CSS and Styles

** app.component.ts **

import { Component } from '@angular/core';
import { HeaderComponent } from './header/header.component';
import { UserInputComponent } from './user-input/user-input.component';

#! Understanding & Configuring View Encapsulation
In Angular, **View Encapsulation** is a mechanism that controls how styles defined in a component are applied and scoped. It helps prevent style conflicts between components by encapsulating styles within each component. There are three main types of view encapsulation strategies available in Angular:

## 1. **Emulated (Default)**
- **Description**: This is the default encapsulation mode in Angular. It emulates the behavior of the Shadow DOM by adding unique attributes to the component's HTML elements. These attributes ensure that styles defined within a component are scoped to that component only.
- **How It Works**: Angular adds a unique attribute (e.g., `_ngcontent`) to the component's elements and applies styles using these attributes. The styles are added to the `` section of the HTML document.
- **Advantages**: It does not require browser support for Shadow DOM, making it compatible with older browsers. It prevents styles from leaking out to other parts of the application.

## 2. **ShadowDom**
- **Description**: This encapsulation mode uses the browser's native Shadow DOM API to encapsulate styles. It creates a Shadow Root for the component, which isolates the component's styles from the rest of the document.
- **How It Works**: When a component uses Shadow DOM encapsulation, Angular creates a Shadow Root for the component. This Shadow Root acts as a boundary, ensuring that styles defined within the component do not affect other parts of the application.
- **Advantages**: It provides true isolation of styles, which can be beneficial for components that need to be reused across different applications or environments. However, it requires browser support for Shadow DOM, which might not be available in older browsers.

## 3. **None**
- **Description**: This encapsulation mode disables style encapsulation entirely. Styles defined in a component are applied globally, meaning they can affect any part of the application.
- **How It Works**: When encapsulation is set to `None`, Angular does not add any special attributes to the component's elements. Styles are applied directly to the document, allowing them to affect any element that matches the CSS selectors.
- **Advantages**: It is useful when you want to share styles across components or apply global styles. However, it can lead to unintended style conflicts if not managed carefully.

Each encapsulation strategy has its use cases depending on the requirements of your application. **Emulated** is suitable for most scenarios due to its compatibility and default behavior. **ShadowDom** offers true isolation but requires modern browser support. **None** is useful for global styling but requires careful management to avoid conflicts.

#? Section - 11 : Working with RxJS (Observables) - Deep Dive

#! What are Observables & What is RxJS?
1. RxJS concepts:
- RxJS is a reactive programming framework that enables handling asynchronous data streams efficiently
- An Observable is a function that returns a stream of values over time, allowing multiple emissions unlike Promises
- Observers are objects with three methods (next, error, complete) that receive notifications from Observables
- Operators are functions that transform, filter, or combine Observable streams into new streams

#! Creating & using an observable
Steps:-
1. Import the required observables from rxjs
2. subscribe to the observable where needed like on ngOnInit()
3. unsubscribe when the component is destroyed like on ngOnDestroy()
"
import { Component, DestroyRef, inject, OnInit } from '@angular/core';
import { interval } from 'rxjs';

@Component({
  selector: 'app-root',
  standalone: true,
  templateUrl: './app.component.html',
})
export class AppComponent implements OnInit {
  private destroyRef = inject(DestroyRef);
  ngOnInit(): void {
    const subscription = interval(1000).subscribe({
      next: (val) => console.log(val),
    });

    this.destroyRef.onDestroy(() => {
      subscription.unsubscribe();
    });
  }
}
"
Steps:-
  a) Observable Creation
    * interval(1000) creates an observable that emits sequential numbers (0, 1, 2, ...) every second
    * Each emission happens exactly 1000 milliseconds apart
    * Without cleanup, this would continue indefinitely

  b) Subscription Management
    * The subscribe method connects to the observable stream
    * The next handler receives each emitted value
    * Values are logged to the console in this example

  c) Modern Cleanup Pattern
    * Uses DestroyRef instead of traditional ngOnDestroy
    * Automatically handles cleanup when the component is destroyed
    * More concise and modern approach compared to older patterns

#! Signals vs Observables
1. refer images

Here's a comprehensive comparison of signals and observables in Angular:

| Feature | Signals | Observables |
| --- | --- | --- |
| **Basic Nature** | A container holding a single value that can be read/written 6:2 | A stream of values over time 6:2 |
| **Access Pattern** | Synchronous read/write operations | Asynchronous subscription-based |
| **Use Case** | UI state management and simple reactive updates 8:1 | Complex async operations and data streams 8:1 |
| **API Complexity** | Simple, focused on state management 8:4 | Rich set of operators, more complex 8:4 |
| **Dependency Tracking** | Automatic dependency tracking 8:3 | Manual subscription management 8:3 |
| **Error Handling** | No built-in error state 5:11 | Built-in error handling 5:2 |
| **Cleanup** | Automatic cleanup in Angular 2:0 | Manual subscription management required 1:3 |

### When to Use Each

**Use Signals When:**

- Managing UI state
- Handling simple reactive updates
- Working with synchronous data
- Building component-level features 8:1

**Use Observables When:**

- Handling asynchronous operations
- Managing complex data streams
- Working with services
- Needing advanced RxJS operators 8:1

### Code Comparison

**Signals:**

```typescript
const countSignal = signal(0);
countSignal.set(countSignal.get() + 1);
console.log(countSignal.get()); // Output: 1
```

**Observables:**

```typescript
const countObservable = of(1).pipe(delay(1000));
countObservable.subscribe(value => console.log(value)); // Output: 1 (after 1 second)
```

### Key Differences

1. **Time Model**  
  - Signals: Synchronous updates, no concept of time 6:6
  - Observables: Asynchronous, values over time 6:6


2. **Reactivity**  
  - Signals: Automatic dependency tracking 8:3
  - Observables: Manual subscription management 8:3


3. **State Management**  
  - Signals: Better for simple state updates 8:5
  - Observables: Better for complex data streams 8:5

This comparison shows that while both signals and observables can handle reactive data, they serve different purposes and are suited for different use cases. Signals are the simpler, more straightforward choice for UI state management, while observables provide more powerful features for complex asynchronous operations.

"
import {afterNextRender,Component,DestroyRef,inject,viewChild} from '@angular/core';
import { FormsModule, NgForm } from '@angular/forms';
import { debounceTime } from 'rxjs';

@Component({
  selector: 'app-login',
  standalone: true,
  imports: [FormsModule],
  templateUrl: './login.component.html',
  styleUrl: './login.component.css',
})
export class LoginComponent {
  private form = viewChild.required<NgForm>('form');
  private destroyRef = inject(DestroyRef);

  constructor() {
    afterNextRender(() => {
      const savedForm = window.localStorage.getItem('saved-login-form');
      
      if (savedForm) {
        const loadedFormData = JSON.parse(savedForm);
        const savedEmail = loadedFormData.email;
        // this.form().setValue({
        //   email: savedEmail,
        //   password: ''
        // })
        setTimeout(()=>{this.form().controls['email'].setValue(savedEmail);}, 10);
      }

      const formRef = this.form();
      const subscription = formRef?.valueChanges?.pipe(debounceTime(500)).subscribe({
        // next: (value) => console.log(value)
        next: (value) =>
          window.localStorage.setItem(
            'saved-login-form',
            JSON.stringify({ email: value.email })
          ),
      });
      this.destroyRef.onDestroy(() => subscription?.unsubscribe());
    });
  }

  onSubmit(formData: NgForm) {
    console.log(formData.form);
    if (formData.form.invalid) {
      console.log('Form is invalid due to angular validators added in the template.');
      return;
    }
    console.log(formData.form.value);
    const enteredEmail = formData.form.value.email;
    const enteredPassword = formData.form.value.password;
    console.log(`Email: ${enteredEmail}, Password: ${enteredPassword}`);

    formData.form.reset();
  }
}

#! Interacting with the Form Programmatically
** login.component.ts **
"
import { Component, DestroyRef, inject, OnInit } from '@angular/core';
import { AbstractControl, FormControl, FormGroup, ReactiveFormsModule, Validators } from '@angular/forms';
import { debounceTime } from 'rxjs';

function mustContainQuestionMark(control: AbstractControl) {
  if (control.value.includes('?')) {
    return null;
  }
  return { doesNotContainQuestionMark: true };
}

let initialEmailValue = ''
const savedForm = window.localStorage.getItem('saved-login-form');

if (savedForm) {
  const loadedForm = JSON.parse(savedForm);
  initialEmailValue = loadedForm.email;
}

@Component({
  selector: 'app-login',
  standalone: true,
  imports: [ReactiveFormsModule],
  templateUrl: './login.component.html',
  styleUrl: './login.component.css',
})
export class LoginComponent implements OnInit {
  private destroyRef = inject(DestroyRef);
  form = new FormGroup({
    // email: new FormControl('', {
    email: new FormControl(initialEmailValue, {
      validators: [Validators.email, Validators.required]
    }),
    password: new FormControl('', {
      validators: [Validators.required, Validators.minLength(6), mustContainQuestionMark]
    }),
  })

  get emailIsInvalid() {
    return this.form.controls['email'].invalid && this.form.controls['email'].touched && this.form.controls['email'].dirty;
  }

  get passwordIsInvalid() {
    return this.form.controls['password'].invalid && this.form.controls['password'].touched && this.form.controls['password'].dirty;
  }

  ngOnInit(): void {
    const savedLoginForm = window.localStorage.getItem('saved-login-form');

    if (savedLoginForm) {
      const loadedFormData = JSON.parse(savedLoginForm);
      // this.form.controls['email'].setValue(loadedFormData.email);
      this.form.patchValue({email: loadedFormData.email});
    }

    const subscription = this.form.valueChanges.pipe(debounceTime(500)).subscribe({
      next: value => {
        window.localStorage.setItem('saved-login-form', JSON.stringify({ email: value.email })); 
      }
    })

    this.destroyRef.onDestroy(() => {subscription.unsubscribe();})
  }

  onSubmit() {
    // console.log(this.form);
    // console.log(this.form.value);
    const enteredEmail = this.form.value.email;
    const enteredPassword = this.form.value.password;
    console.log(`Email: ${enteredEmail}, Password: ${enteredPassword}`);
  }
}

#? Section - 16: Deploying Angular Apps - CSR, SSR, SGA

#! Module Introduction
1. We will learn different ways to deploy an Angular app.

#! Preparing a Project For Deployment: Building It For Production
1. Run "ng build" or "npm run build".
2. After the build is successful, you will see the dist folder in the project root.
3. This is the production build.
4. This is a SPA (Single Page Application) build which is the default one.

#! Building SPAs: Pros and Cons
Pros:-
  1. SPAs are client side only web applications.
  2. All code executes in the browser.
  3. No dynamic web server needed - a static host suffices
  
Cons:-
  1. Initial missing content.
  2. Bad SEO.

#! SPAs : Deployment Example
1. Search the web for "static web hosts".
2. You will get various providers like firebase, heroku, netlify, hostinger, etc.
3. We will use firebase for this example because it is free and google based.
4. Go to firebase and create a new project.
5. Click on the "Add Firebase to your web app" button.
6. Setup Firebase Hosting, first "npm install -g firebase-tools", then "firebase login", then "firebase init".
7. Fill in the required options (refer video).
8. Now use "firebase deploy" to deploy the app. Make sure you have run the "ng build" command.

#! Using "ng add", "ng deploy" & Angular's Built-in Deployment Support
1. You can also use the deployment feature provided by Angular which already has support to various deployment platforms like Firebase, Netlify, Heroku, etc.
Refer => https://angular.dev/tools/cli/deployment

#! Server-side Rendering (SSR) Introduction
Pros:-
  1. Angular app routes are rendered on-demand on a dynamic web server.
  2. Browser receives finished, rendered page.
  3. Web app is hydrated("activated") and becomes a SPA after the initial rendering.
  4. Dynamic web server is required.

Cons:-
  1. Long-taking tasks may cause empty pages
  2. Increased and unwanted complexity.

#! Setting Up SSR For An Angular App
1. ng add @angular/ssr
2. You will get a main.server.ts file which is the main server file for the application.

Refer => https://angular.dev/guide/ssr

#! Building and Service an SSR App
1. ng add @angular/ssr
2. ng build
3. npm run serve:ssr:routing
4. You will get a new address i.e http://localhost:4000.

#! Authoring SSR-ready Code (Beware of Pitfalls!)
1. We get the "locatStorage" not defined error.
2. Refer video for solution.

#! SSR and Client-Server Mismatches
1. Refer video

#! Static Site Generation (SSG) Introduction
Pros:-
  1. Angular app routes are pre-rendered at build time.
  2. Browser receives finished, rendered page.
  3. Web app is hydrated("activated") and becomes a SPA after the initial rendering.
  4. Dynamic web server is required.

Cons:-
  1. No dynamic server side data fetching.

#! Configuring & Using SSG

2. ng build
